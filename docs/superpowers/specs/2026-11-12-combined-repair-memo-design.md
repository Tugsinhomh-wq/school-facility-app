# บันทึกข้อความขอซ่อมแซมรวมหลายงาน (อาคารเดียวกัน) — design

สถานะ: ร่าง รอผู้ใช้ตรวจสเปก · 2026-11-12
ผู้ใช้อนุมัติการออกแบบในแชทแล้ว 2 ส่วน (การทำงานของหน้าจอ และฐานข้อมูล/ผลต่อหน้าอื่น)

## 1. ทำไมต้องทำ

ตอนนี้หน้า `/memos` สร้างร่างบันทึกข้อความได้ครั้งละ **1 งานซ่อมต่อ 1 บันทึก** (`createMemoFromTicket`, ผูกด้วย `memorandums.reference_id` ตัวเดียว)
เมื่ออาคารเดียวกันมีงานค้างหลายงาน เจ้าหน้าที่ต้องทำบันทึกแยกทีละฉบับ แล้วเสนอผู้อำนวยการหลายรอบ

ที่ต้องการ: เจ้าหน้าที่ **ติ๊กเลือกงานในอาคารเดียวกัน แล้วกดปุ่มรวมเป็นร่างเดียว** เพื่อเสนอผู้อำนวยการครั้งเดียว
ร่างนี้เป็นร่างเสนอเพื่อ **ขออนุมัติซ่อม** (ไม่มีส่วนค่าใช้จ่ายประมาณการในรอบนี้)

ความสำเร็จ: เลือก 2–20 งานของอาคารเดียวกัน กดปุ่มเดียว ได้ร่างบันทึกฉบับเดียวที่แก้ได้ ส่งออก PDF/Word ได้เหมือนร่างปกติ และงานเหล่านั้นไม่โผล่ในรายการ "ยังไม่มีบันทึก" อีก

## 2. ขอบเขต

ทำ:
- ช่องติ๊กและปุ่ม "รวมเป็นร่างเดียว" ในรายการงานซ่อมที่ยังไม่มีบันทึก
- ฟังก์ชันฐานข้อมูลสร้างบันทึกรวมแบบ atomic พร้อมตรวจเงื่อนไข
- ตัวสร้างข้อความร่างรวม (รายการเป็นข้อ พร้อมยอดรวมจำนวนงาน)
- ปรับ logic "งานนี้มีบันทึกแล้ว" ให้นับบันทึกรวมด้วย
- เพิ่มตารางใหม่เข้ารายการสำรองข้อมูล

ไม่ทำในรอบนี้:
- ค่าใช้จ่ายประมาณการและยอดเงินรวม
- แก้รายการงานในบันทึกรวมหลังสร้าง (ถ้าจะเพิ่ม/ตัดงาน ให้ลบร่างแล้วสร้างใหม่)
- ตัวเลขจำนวนบันทึกในหน้าถังขยะ (`list_trashed_tickets` ยังนับเฉพาะบันทึกเดี่ยว)
- เปลี่ยนการทำงานของบันทึกเดี่ยวที่มีอยู่แล้ว

## 3. ผู้ใช้และสิทธิ์

เจ้าหน้าที่ (`staff`) และผู้ดูแลระบบ (`super_admin`) เท่านั้น ตรงกับสิทธิ์สร้างบันทึกข้อความเดิม
เจ้าหน้าที่ห้องประชุม (`room_staff`) ไม่เห็นงานซ่อมในหน้า `/memos` อยู่แล้ว จึงไม่เห็นฟีเจอร์นี้

## 4. ฐานข้อมูล — `supabase/memo_tickets.sql`

รันซ้ำได้ปลอดภัย (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP POLICY IF EXISTS`) ผมไม่รันกับ Supabase จริง ผู้ใช้เป็นคนรัน

**ตาราง `memo_tickets`**

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `memo_id` | UUID | FK → `memorandums(id)` ON DELETE CASCADE |
| `ticket_id` | UUID | FK → `repair_tickets(id)` ON DELETE CASCADE, **UNIQUE** |
| `position` | INT | ลำดับข้อในร่าง (เริ่ม 1) |

- Primary key `(memo_id, ticket_id)`; `UNIQUE (ticket_id)` ทำให้ 1 งานอยู่ได้แค่ 1 บันทึกรวม
- RLS เปิด: SELECT/INSERT สำหรับ `staff`, `super_admin` (ใช้ `public.current_role_is`) ไม่มี UPDATE/DELETE policy (ลบผ่าน cascade จากการลบบันทึก)
- Index บน `ticket_id` มีอยู่แล้วจาก UNIQUE

**ฟังก์ชัน `public.create_combined_repair_memo(p_ticket_ids UUID[], p_subject TEXT, p_recipient TEXT, p_body TEXT, p_proposal TEXT) RETURNS UUID`**

- `SECURITY INVOKER` (RLS ของผู้เรียกยังมีผล), `SET search_path = public`
- ตรวจตามลำดับ ถ้าข้อใดไม่ผ่าน `RAISE EXCEPTION` และไม่สร้างอะไรเลย:
  1. ผู้เรียกเป็น `staff`/`super_admin`
  2. จำนวนงานที่ไม่ซ้ำกัน 2–20
  3. ทุกงานมีอยู่จริง (งานในถังขยะถูกซ่อนด้วย RLS จึงนับว่าไม่มี)
  4. ทุกงานอยู่ `building_id` เดียวกัน
  5. ทุกงานมีสถานะ `pending` หรือ `in_progress`
  6. ไม่มีงานใดอยู่ใน `memo_tickets` และไม่มีงานใดมีบันทึกเดี่ยว (`memorandums.origin_module = 'repair' AND reference_id = ticket_id`)
- สร้างแถวใน `memorandums`: `origin_module = 'repair'`, `reference_id = NULL`, `author_id = auth.uid()`, `approval_mode = 'paper_hybrid'`, `doc_ref_no = ''` (trigger ออกเลข `MEMO-…` ให้เหมือนเดิม)
- ใส่แถวใน `memo_tickets` ตามลำดับเวลาแจ้งของงาน (เก่าก่อน) แล้วคืน id ของบันทึก
- ชนกันตอนสองคนรวมงานเดียวกันพร้อมกัน: unique violation (`23505`) → ทั้ง transaction ย้อนกลับ

## 5. ฝั่งแอป

**`src/lib/memo/draft.ts` — `draftFromTickets(tickets, author)`** (ฟังก์ชันล้วน มีเทสต์)
- `subject`: `ขออนุมัติซ่อมแซมอาคารสถานที่ {ชื่ออาคาร} จำนวน {N} รายการ`
- `recipient`: `ผู้อำนวยการ{SCHOOL_NAME}` เหมือนร่างเดี่ยว
- `body_content` (แต่ละย่อหน้าคั่นด้วย newline เหมือนเดิม):
  1. ย่อหน้าเปิด: ด้วยงานอาคารสถานที่ได้รับแจ้งความชำรุดเสียหาย ณ {อาคาร} รวม {N} รายการ และตรวจสอบสภาพแล้ว พบว่ามีความจำเป็นต้องซ่อมแซม (ใช้คำว่า "อย่างเร่งด่วน" ถ้ามีงาน `high`/`emergency` อย่างน้อยหนึ่งงาน)
  2. รายการเป็นข้อ `1.`, `2.`, … แต่ละข้อ: สถานที่ (อาคาร + ห้อง/จุด), ความเสียหาย (ชื่อเรื่อง + รายละเอียดถ้าต่างกัน), เลขที่งาน, วันที่แจ้ง (`formatThaiDate`) และบันทึกช่าง (`technician_notes`) ถ้ามี
  3. บรรทัดสรุป: `รวมทั้งสิ้น {N} รายการ`
- `proposal`: ว่าง (ข้อความขออนุมัติคือ `REPAIR_CLOSING` ที่ renderer เติมให้อยู่แล้ว)
- ไม่มีส่วนค่าใช้จ่าย; ไม่แตะ `estimated_cost`

**`src/app/(dashboard)/memos/actions.ts` — `createCombinedMemo(formData)`**
- อ่าน `ticket_ids` (หลายค่า), ตรวจเป็น UUID และ 2–20 รายการ
- โหลดงานพร้อมอาคาร/ห้อง/ผู้แจ้ง และโปรไฟล์ผู้เขียน แล้วเรียก `draftFromTickets`
- เรียก RPC `create_combined_repair_memo` แล้ว `revalidatePath("/memos")`, `"/"` และ `redirect` ไป `/memos/{id}`
- ข้อผิดพลาด redirect กลับ `/memos?error=…` ด้วยข้อความไทยตามสาเหตุ (ต่างอาคาร, งานปิดแล้ว, มีบันทึกแล้ว/ชนกัน, ไม่ใช่เจ้าหน้าที่)
- โหมดสาธิต (ไม่มี Supabase) พาไปบันทึกตัวอย่างแรก เหมือน `createMemoFromTicket`

**`src/lib/data/memos.ts`** — `getMemoList` โหลด `memo_tickets.ticket_id` แล้วรวมกับ `reference_id` ของบันทึกเดี่ยว เป็นชุด "used"; โหลดไม่สำเร็จ = `failed` เหมือนเดิม

**`createMemoFromTicket`** — ก่อนสร้างร่างเดี่ยว ตรวจ `memo_tickets` ด้วย ถ้างานอยู่ในบันทึกรวมให้ `redirect` ไปบันทึกนั้น (ปุ่มในหน้ารายละเอียดงานซ่อมจึงเปิดบันทึกรวมให้)

**`src/lib/backup.ts`** — เพิ่ม `"memo_tickets"` ต่อจาก `"memorandums"` (ลูกต้องอยู่หลังแม่ทั้งสองตาราง) และเพิ่ม `memo_tickets: ["memo_id", "ticket_id"]` ใน `ORDER_BY` เพราะไม่มีคอลัมน์ `id`

## 6. หน้าจอ — `/memos`

- ในรายการ "งานซ่อมที่ยังไม่มีบันทึก" แต่ละงานมีช่องติ๊ก (พื้นที่กดสูง/กว้างอย่างน้อย 44px) ปุ่มเดิม "ร่างบันทึกข้อความ" ยังอยู่ทำงานเหมือนเดิม
- พอติ๊กงานแรก งานของอาคารอื่นถูกปิดไม่ให้ติ๊ก (disabled พร้อมข้อความบอกเหตุผลที่อ่านได้ ไม่ใช่แค่สีจาง)
- แถบด้านบนรายการแสดง "เลือกแล้ว N งาน · {ชื่ออาคาร}" และปุ่ม **รวมเป็นร่างเดียว** ปรากฏเมื่อเลือกตั้งแต่ 2 งาน; มีปุ่มล้างที่เลือก; เกิน 20 งานปิดปุ่มพร้อมบอกเหตุผล
- ส่วนที่โต้ตอบ (ติ๊ก/แถบ) เป็น client component เล็กๆ ครอบฟอร์มเดียวที่ส่ง `ticket_ids` หลายค่า ส่วนอื่นของหน้ายังเป็น server component
- ขณะส่ง ปุ่มแสดงสถานะรอและกดซ้ำไม่ได้ (กันกดสองครั้ง); ถ้ากดซ้ำจริง ฐานข้อมูลปฏิเสธรอบที่สองเพราะงานมีบันทึกแล้ว

## 7. การทดสอบและการตรวจ

- เทสต์ใหม่ `src/lib/memo/draft.test.ts` (node:test, import แบบ relative `.ts`): ชื่ออาคาร/จำนวนในหัวเรื่อง, เลขข้อและลำดับตามเวลาแจ้ง, "เร่งด่วน" เฉพาะเมื่อมีงาน high/emergency, บรรทัดสรุปยอด, ไม่มีคำว่าบาท/ค่าใช้จ่าย, งานที่ไม่มีห้องใช้ `location_detail`, `technician_notes` ปรากฏเมื่อมี
- `npm test`, `npx eslint` ไฟล์ที่แก้, `npx tsc --noEmit` (มี error เดิม `LayoutProps` ใน `layout.tsx` อยู่ก่อนแล้ว ตรวจว่าไม่มี error ใหม่)
- ตรวจ SQL: อ่านทบทวนเท่านั้น (ไม่มี Supabase ในสภาพแวดล้อมนี้ให้รัน) มี check block เป็นคอมเมนต์ท้ายไฟล์ให้ผู้ใช้รันเทียบหลังรัน SQL: รวมต่างอาคาร → error, รวมงานที่ปิดแล้ว → error, รวมงานที่มีบันทึกแล้ว → error, รวม 1 งาน → error, สำเร็จ → ได้บันทึก 1 ฉบับ + `memo_tickets` ครบ
- จะรายงานตรงๆ ว่าไม่ได้ลองบนเว็บจริง และ SQL ยังไม่ได้รันกับฐานข้อมูลจริง

## 8. ลำดับขึ้นระบบ

1. ผู้ใช้รัน `supabase/memo_tickets.sql` ใน Supabase SQL Editor
2. จึง merge PR (ถ้า merge ก่อน หน้า `/memos` จะโหลดไม่ขึ้นจนกว่าจะรัน SQL เพราะ `getMemoList` อ่านตารางใหม่)
3. หลัง deploy ให้ลองรวม 2 งานของอาคารเดียวกันด้วยบัญชีเจ้าหน้าที่

## 9. ความเสี่ยงและข้อสมมติ

- สมมติว่างานที่เป็น "รายงานซ้ำ" (`duplicate_of` ไม่ว่าง) ยังติ๊กรวมได้เหมือนที่รายการเดิมไม่ได้กรองไว้; ไม่เปลี่ยนพฤติกรรมนี้ในรอบนี้
- ถ้างานในบันทึกรวมถูกลบถาวรจากถังขยะ ลิงก์ใน `memo_tickets` หายตาม (cascade) แต่ข้อความในบันทึกยังอยู่ เพราะเป็นข้อความที่คัดลอกมา
- เพดาน 20 งานเป็นค่าที่ผมเลือกเพื่อให้บันทึกยาวไม่เกินสองสามหน้า ปรับได้ที่เดียวในฟังก์ชันและ action
