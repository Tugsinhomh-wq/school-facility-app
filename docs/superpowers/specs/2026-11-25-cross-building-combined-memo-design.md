# บันทึกข้อความรวมหลายงาน ข้ามอาคารได้ และรวมงานชนิดเดียวกันเป็นข้อเดียว — design (ฉบับสั้น)

สถานะ: ร่าง รอผู้ใช้อนุมัติ · 2026-11-25

## 1. ทำไมต้องทำ

งานชนิดเดียวกันมักเกิดคนละอาคาร (เช่น สาย HDMI เสีย, หน้าต่างเสีย) แต่ร่างบันทึกรวมใน `/memos` บังคับอาคารเดียว
และแตกเป็น 1 ข้อต่อ 1 งาน เจ้าหน้าที่จึงต้องทำหลายฉบับ และข้อความถึง ผอ. ซ้ำซ้อน

ที่ต้องการ: เลือกงานข้ามอาคารได้ และงานชนิดเดียวกันรวมเป็น **ข้อเดียว** ที่ระบุอาคาร/ห้องของแต่ละจุด
(เช่น "1. สาย HDMI ชำรุด 3 จุด ได้แก่ …")

## 2. ขอบเขต

ทำ:
- เลิกจำกัดอาคารเดียวทั้งหน้าจอ (`selectableTicket`), action และฟังก์ชัน SQL (`mixed_buildings`)
- ในแถบรวมงาน งานที่ติ๊กแต่ละงานเลือก "ข้อ" ได้ (ค่าเริ่มต้น = เป็นข้อของตัวเอง) งานที่เลือกข้อเดียวกันจะถูกรวมเป็นข้อเดียวในร่าง
- `draftFromTickets` จัดข้อตามกลุ่ม และรองรับหลายอาคาร

ไม่ทำ:
- จัดกลุ่มอัตโนมัติ / ช่อง "ประเภทงาน" ในฟอร์มแจ้งซ่อม (ทางเลือก B เก็บไว้ทำภายหลัง)
- เก็บกลุ่มลงฐานข้อมูล: กลุ่มมีผลเฉพาะตอนสร้างร่าง `memo_tickets` ยังผูกรายงานรายงานเหมือนเดิม
- แก้บันทึกรวมที่สร้างไปแล้ว, เตือนงานซ้ำ (`similar_open_tickets`), `duplicate_of`
- ค่าใช้จ่ายประมาณการ

## 3. แนวทางที่พิจารณา

- **A (เลือก):** ปลดล็อกข้ามอาคาร เจ้าหน้าที่จัดกลุ่มเอง — แม่น ไม่ต้องเพิ่มข้อมูล เสี่ยงต่ำ
- B: เพิ่มช่องประเภทงานแล้วจัดกลุ่มอัตโนมัติ — ต้องเพิ่มคอลัมน์/ฟอร์ม/SQL งานเก่าไม่มีประเภท ผู้แจ้งอาจเลือกผิด

## 4. พฤติกรรม

หน้าจอ (`candidate-list.tsx`)
- ติ๊กงานจากอาคารใดก็ได้ ไม่มีข้อความ "ต่างอาคาร…" อีก; แถบบนแสดง "เลือกแล้ว N งาน · M อาคาร"
- งานที่ติ๊กแล้วมีตัวเลือก "ข้อ": ข้อของตัวเอง / กลุ่ม 1 / กลุ่ม 2 … (ส่งเป็นค่าใน form ควบคู่ `ticket_ids`)
- คงขั้นต่ำ 2 งาน สูงสุด 20 งาน (ตามจำนวนงาน ไม่ใช่จำนวนข้อ)

ร่างข้อความ (`draftFromTickets(tickets, groups)`)
- งานเรียงตามเวลาแจ้ง; ข้อเรียงตามงานแรกของแต่ละกลุ่ม
- ข้อที่มีงานเดียว: รูปแบบเดิม
- ข้อที่มีหลายงาน: ชื่อข้อใช้ชื่อเรื่องของงานแรกในกลุ่ม + "จำนวน K จุด" แล้วตามด้วยสถานที่ (อาคาร + ห้อง/จุด) เลขที่งาน วันที่แจ้ง ของแต่ละงาน
- หัวเรื่อง: อาคารเดียว = รูปแบบเดิม; หลายอาคาร = `ขออนุมัติซ่อมแซมอาคารสถานที่ จำนวน N รายการ` ย่อหน้าเปิดระบุรายชื่ออาคารที่เกี่ยวข้อง
- บรรทัดสรุป: `รวมทั้งสิ้น N รายการ` (N = จำนวนงาน)
- เจ้าหน้าที่แก้ข้อความได้ในหน้าแก้ไขบันทึกเหมือนเดิม จึงแก้ชื่อข้อได้ภายหลัง

SQL (`memo_tickets.sql`, `CREATE OR REPLACE` รันซ้ำได้)
- ตัดการตรวจ `building_n <> 1` และ error `mixed_buildings`; เงื่อนไขอื่นเหมือนเดิม
- อัปเดต check block ท้ายไฟล์: รวมต่างอาคารต้องสำเร็จ

## 5. ข้อจำกัด / ความเสี่ยง

- ต้องรัน SQL ใหม่ใน Supabase (ทำตามสกิล supabase-sql-rollout) ก่อน/พร้อม deploy ไม่งั้นฟังก์ชันเดิมยังปฏิเสธต่างอาคาร
- โค้ดอื่นที่สมมติว่าบันทึกรวมมีอาคารเดียว (หน้ารายละเอียดบันทึก, ภาพแนบ, ส่งออก PDF/Word) ต้องตรวจและแก้ถ้ามี
- ไม่มี Supabase ในสภาพแวดล้อมนี้: SQL ตรวจโดยอ่านทบทวน และจะรายงานตรงๆ ว่ายังไม่ได้รันจริง

## 6. การทดสอบ

- แก้ `combine.test.ts` (ไม่มีกติกาอาคารเดียว) และ `draft.test.ts` เพิ่มกรณี: ข้ามอาคาร, หลายงานในข้อเดียว, ข้อเดี่ยวปนกลุ่ม, หัวเรื่องหลายอาคาร, ลำดับข้อ
- `npm test`, `npx eslint` ไฟล์ที่แก้, `npx tsc --noEmit`

## 7. ปล่อยให้ผู้สร้างตัดสินใจ

- หน้าตาตัวเลือก "ข้อ" (select หรือช่องตัวเลข) ขอให้พื้นที่กดอย่างน้อย 44px
- รูปแบบการเรียงสถานที่ในข้อรวม (ย่อหน้าเดียวคั่นด้วยเครื่องหมาย หรือแยกบรรทัดย่อย) ตามที่ตัว render PDF/Word รองรับ
