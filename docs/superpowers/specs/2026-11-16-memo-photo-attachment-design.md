# แนบรูปแจ้งซ่อมที่ด้านหลังบันทึกข้อความ — design

สถานะ: ร่าง รอผู้ใช้ตรวจสเปก · 2026-11-16
ผู้ใช้เลือกแนวทางแล้วในแชท: ทำครบทุกที่ (PDF, Word ทั้งสองตัวสร้าง, หน้าพรีวิว) ใช้เฉพาะรูปก่อนซ่อม

## 1. ทำไมต้องทำ

บันทึกข้อความเรื่องแจ้งซ่อมถูกปริ้นแนบกระดาษเสนอผู้อำนวยการเซ็น ตอนนี้บันทึกมีแต่ข้อความ
ผู้อำนวยการต้องเชื่อคำบรรยาย ไม่เห็นสภาพจริง ทั้งที่ผู้แจ้งถ่ายรูปแนบไว้ในงานแล้ว (`repair_tickets.image_urls`)

ที่ต้องการ: เวลาส่งออกบันทึกข้อความเรื่องแจ้งซ่อม รูปของงานนั้นต่อท้ายเป็นหน้าแนบ พร้อมปริ้นได้เลย

ความสำเร็จ: กดส่งออก PDF หรือ Word ของบันทึกซ่อม (เดี่ยวหรือรวม) แล้วได้เอกสารที่ท้ายเล่มมีหน้ารูป
หน้าพรีวิวบนจอแสดงหน้ารูปเดียวกัน และงานที่ไม่มีรูปได้เอกสารเหมือนเดิมทุกประการ

## 2. ขอบเขต

ทำ:
- ตัวโหลดรูปของบันทึกซ่อม (เดี่ยวและรวม) ด้วยสิทธิ์ของผู้ใช้ที่เปิดหน้า/กดส่งออก
- หน้า "เอกสารแนบ: ภาพประกอบการแจ้งซ่อม" ต่อท้าย PDF, Word (python-docx และ docx-js สำรอง) และพรีวิว
- คำบรรยายใต้รูปจากข้อมูลที่ผู้แจ้งกรอกไว้เท่านั้น

ไม่ทำ:
- รูปหลังซ่อม (`after_image_urls`) เพราะบันทึกนี้ขออนุมัติซ่อม
- ให้ระบบอ่านรูปแล้วเขียนคำบรรยายเอง
- เลือก/ตัด/เรียงรูปในบันทึก (ใช้รูปทั้งหมดของงาน)
- บันทึกข้อความประเภทอื่น (ห้องประชุม, ทั่วไป) ไม่เปลี่ยน
- เปลี่ยนฐานข้อมูล, สิทธิ์ หรือ storage (ไม่มี SQL ใหม่)

## 3. ข้อมูลที่ใช้

- รูป: `repair_tickets.image_urls` (path ใน bucket `repair-images` แบบ private สูงสุด 4 รูป/งาน, ตอนอัปโหลดถูกย่อเป็น JPEG ราว 300 KB และลบ EXIF แล้ว)
- บันทึกเดี่ยว: `memorandums.origin_module = 'repair'` และ `reference_id` = งานเดียว
- บันทึกรวม: `memo_tickets` เรียงตาม `position` (ข้อ 1, 2, …) ตรงกับเลขข้อที่ `draftFromTickets` ใส่ในเนื้อบันทึก
- ผู้อ่านรูปได้ตาม storage policy เดิม (เจ้าหน้าที่/ผู้ดูแลระบบ, หรือเจ้าของรูป) ไม่ต้องเพิ่มสิทธิ์

## 4. ฝั่งแอป

**ตัวโหลด `src/lib/data/memo-photos.ts` — `getMemoPhotos(memo)`**
- คืน `MemoPhotoGroup[]` = `{ heading, photos: { url }[] }`:
  - บันทึกเดี่ยว: 1 กลุ่ม; บันทึกรวม: 1 กลุ่มต่อ 1 งาน ตามลำดับ `position`
  - `heading` = `{สถานที่} – {ชื่อเรื่อง}` (สถานที่ = อาคาร + ห้อง/จุด ตรงกับ `placeOfTicket` ใน `draft.ts`); บันทึกรวมนำหน้าด้วย `ข้อ N`
  - ไม่มีชื่อเรื่อง → ไม่ใส่คำบรรยาย ไม่เติมข้อความเอง; งานไม่มีรูปไม่มีกลุ่ม
- สร้างลิงก์ชั่วคราว (`createSignedUrls`, 3600 วินาที) ผ่าน client ของผู้ใช้ที่ล็อกอิน
- ไม่ใช่บันทึกซ่อม หรือโหมดสาธิต (ไม่มี Supabase) → คืน `[]`
- โหลดข้อมูลไม่สำเร็จ → คืน `[]` และ `console.warn` ไม่ทำให้ส่งออกล้ม

**โมเดล `src/lib/memo/model.ts`**
- `MemoDoc` ไม่เปลี่ยน; เพิ่ม type `MemoPhotoGroup` และ `LoadedPhotoGroup` (กลุ่มที่โหลดไบต์แล้ว: `{ heading, photos: ({ data: Buffer; width; height } | { failed: true })[] }`)

**ดาวน์โหลดไบต์ `src/lib/memo/photo-files.ts` — `loadPhotoFiles(groups)`** (ใช้โดยเส้นทางส่งออกเท่านั้น)
- `fetch` ลิงก์ที่เซ็นแล้ว ทีละไม่เกิน 6 รูปพร้อมกัน, timeout 10 วินาที/รูป, เพดานรวม 80 รูป
- อ่านความกว้างยาวจากหัวไฟล์ JPEG/PNG (ฟังก์ชันเล็กๆ ไม่เพิ่ม dependency); ชนิดอื่นหรืออ่านไม่ได้นับเป็น `failed`

**เส้นทางส่งออก `memos/[id]/pdf/route.ts` และ `docx/route.ts`**
- หลัง `getMemo` เรียก `getMemoPhotos` แล้ว `loadPhotoFiles` ส่งต่อให้ `memoToPdf(doc, photos)` / `memoToDocx(doc, photos)` / `memoToDocxPython(doc, photos)`

**หน้าตาหน้าแนบ (ทุก renderer เหมือนกัน)**
- เริ่มหน้าใหม่ หัวเรื่องตรงกลางตัวหนา `เอกสารแนบ: ภาพประกอบการแจ้งซ่อม`
- รูปเรียง 2 คอลัมน์ กรอบรูปไม่เกินกว้าง 7.6 cm × สูง 8.5 cm (ย่อให้พอดีกรอบ คงสัดส่วน ไม่ตัดรูป) ใช้ขอบกระดาษเดียวกับบันทึก
- ใต้รูปทุกรูปมีคำบรรยาย `heading` ของกลุ่มนั้น ตัวอักษร 12–14 pt
- แถวไม่ถูกตัดข้ามหน้า; รูปไม่พอหน้าเดียวก็ขึ้นหน้าถัดไป
- รูปที่ `failed` แสดงกรอบเปล่าพร้อมข้อความ `ไม่สามารถโหลดรูปนี้ได้` แทนรูป
- ไม่มีรูปเลย → ไม่มีหน้าแนบ ไฟล์เหมือนเดิม

**ตัวสร้างไฟล์**
- `pdf.ts` (pdfkit): `pdf.image(data, { fit })` ต่อจากส่วนเดิมด้วย `addPage()`
- `docx.ts` (docx-js, ตัวสำรอง): `ImageRun` ในตารางไร้เส้น 2 คอลัมน์ ใช้ขนาดจากหัวไฟล์
- `scripts/memo_docx.py` + `docx-python.ts`: ส่งรูปเป็น base64 ใน JSON เดียวกับ MemoDoc (`photos`) แล้วใส่ตารางไร้เส้น 2 คอลัมน์; ตัวสร้างทั้งสองต้องให้หน้าตาตรงกัน
- `memo-preview.tsx`: หน้าแนบเป็นหน้า A4 เพิ่มต่อจากหน้าบันทึก (หน่วย `cqw` เหมือนเดิม) ใช้ลิงก์ที่เซ็นแล้วตรงๆ ใน `<img>`; `memos/[id]/page.tsx` เรียก `getMemoPhotos` แล้วส่ง `photos` ผ่าน `MemoEditor` ไปพรีวิว
- ข้อความ `ไฟล์ใช้ข้อความที่บันทึกล่าสุด` ใต้ปุ่มส่งออกคงเดิม

## 5. การทดสอบและการตรวจ

- เทสต์ใหม่ (node:test เหมือนไฟล์เทสต์เดิม): ตัวอ่านขนาดรูป JPEG/PNG, การจัดหัวข้อ/ลำดับ `ข้อ N` ของกลุ่ม, งานไม่มีรูปไม่มีกลุ่ม
- เพิ่มใน `pdf.test.ts` / `docx.test.ts`: ไม่มีรูป → ผลเท่าเดิม; มีรูป → PDF มีหน้าเพิ่ม, .docx มีไฟล์ใน `word/media/` เพิ่มจากตราครุฑ; รูป `failed` ไม่ทำให้ล้ม
- รัน `scripts/memo_docx.py` จริงถ้าสภาพแวดล้อมมี Python + python-docx เพื่อดูว่า .docx เปิดได้ (ไม่มี → รายงานว่าไม่ได้ลอง)
- `npm test`, `npx eslint` ไฟล์ที่แก้, `npx tsc --noEmit` (มี error เดิม `LayoutProps` ใน `layout.tsx` ตรวจว่าไม่มี error ใหม่)
- จะรายงานตรงๆ ว่าไม่ได้ลองกับ Supabase/storage จริงและไม่ได้ปริ้นบนกระดาษ

## 6. ลำดับขึ้นระบบ

ไม่มี SQL ใหม่ merge แล้ว deploy ได้เลย หลัง deploy ให้ลองส่งออกบันทึกซ่อมที่มีรูป (เดี่ยว 1 ฉบับ และรวม 2 งาน) ทั้ง PDF และ Word แล้วลองปริ้น

## 7. ความเสี่ยงและข้อสมมติ

- เลขข้อ (`ข้อ N`) มาจาก `memo_tickets.position`; ถ้าเจ้าหน้าที่แก้ข้อความในบันทึกจนเลขข้อไม่ตรงลำดับเดิม คำบรรยายใต้รูปจะไม่ตามไปด้วย (ไม่แก้ในรอบนี้)
- บันทึกรวม 20 งานอาจมีรูปถึง 80 รูป (ราว 24 MB ในหน่วยความจำ) ส่งออกอาจช้า; เพดาน 80 รูปและ timeout กันค้าง รูปเกินเพดานข้ามไปและต่อท้ายด้วยบรรทัดแจ้งว่าแสดงไม่ครบ
- ลิงก์รูปในพรีวิวหมดอายุใน 1 ชั่วโมง; โหลดหน้าใหม่แล้วได้ลิงก์ใหม่ (พฤติกรรมเดียวกับหน้ารายละเอียดงานซ่อม)
- งานที่ถูกย้ายลงถังขยะ RLS ซ่อนอยู่ รูปของงานนั้นจะไม่ขึ้น (ถือเป็นพฤติกรรมที่ยอมรับได้)
